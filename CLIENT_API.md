# Building a Butler Client

Butler exposes two APIs you can build against, depending on what you're making:

1. **Subsonic-compatible REST API** (`/rest/*`) -- if you want your client to also work with existing Subsonic apps (DSub, Symfonium, Substreamer, play:Sub, Amperfy...), or you're extending one of those. Fully documented below, stable, versioned against the real [Subsonic API spec](http://www.subsonic.org/pages/api.jsp) plus a few [OpenSubsonic](https://opensubsonic.netlify.app/) extensions.
2. **Butler's native REST API** (everything else) -- if you're building a Butler-specific client (like the official web app or Android app) and want the full feature set: real synced lyrics, Daily Mix, Spotify import, admin controls, SSO, etc. This is documented at a high level below; treat `https://your-server/docs` (Swagger UI, auto-generated by FastAPI) as the source of truth for exact request/response shapes and any endpoint not covered here.

> Both sections below were written and verified directly against a live running instance -- the Subsonic layer via real client-shaped requests, the native API via the live `/openapi.json` schema plus real captured request/response pairs, not from memory or guesswork.

## Authentication

Butler has two independent login systems that both ultimately produce the same kind of session:

### Native JWT auth
```
POST /auth/register   { username, password, invite_code }  -> { token, username }
POST /auth/login       { username, password }               -> { token, username }
GET  /auth/me          (Bearer token)                        -> { id, username, created_at }
POST /auth/change-password  { old_password, new_password }
```
Send the token back as `Authorization: Bearer <token>` on every subsequent request. Tokens don't expire on a short cycle -- there's no refresh-token dance, just re-login if a request 401s.

New accounts need an **invite code** from an admin, except the very first account ever created on a fresh server, which becomes the admin automatically.

### SSO (OIDC)
```
GET /auth/oidc/status   -> { enabled, providers: [{ key, display_name }] }
GET /auth/oidc/login?provider=<key>&invite=<code>&client=web|android
```
`client` controls how the token comes back once the provider redirects to `/auth/oidc/callback`:
- `web` (default): redirects to `/#oidc_token=<jwt>` -- read the token from the URL fragment, never sent to the server or logged.
- `android`: redirects to a custom-scheme deep link, `com.butler.music://oidc-callback?token=<jwt>` -- only relevant if you're building an Android client and want to reuse Butler's own OIDC flow rather than rolling your own.

Either way you end up with the same JWT `/auth/login` would have given you -- use it identically.

A brand-new SSO identity needs an invite code the first time (`?invite=`), exactly like registration, unless the server has no users yet.

### Minimal client walkthrough

The smallest possible native client -- log in, list the library, play a song:

```bash
# 1. Log in
TOKEN=$(curl -s -X POST https://your-server/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"you","password":"yourpassword"}' | jq -r .token)

# 2. List your library
curl -s https://your-server/library -H "Authorization: Bearer $TOKEN"

# 3. Stream a song by youtube_id (from step 2's results)
curl -s https://your-server/songs/stream/dQw4w9WgXcQ -H "Authorization: Bearer $TOKEN" -o song.mp3
```

The Subsonic-compatible equivalent, for comparison -- no bearer token, credentials go in every request's query string instead:

```bash
BASE="https://your-server/rest"
AUTH="u=you&p=yourpassword&v=1.16.1&c=myclient&f=json"

curl -s "$BASE/getAlbumList2.view?$AUTH&type=newest&size=20"
curl -s "$BASE/stream.view?$AUTH&id=<song-id-from-above>" -o song.mp3
```

Everything else in this document is filling in the detail around this same shape.

### API keys

SSO accounts get a locked, random, unrecoverable password under the hood -- there's no real password an SSO-only user could type into a third-party Subsonic client or script. API keys solve that: any user (SSO or not) can generate one from account settings (or `POST /auth/api-keys`), and use it exactly like a password -- both the Subsonic layer's `p=` parameter and native `/auth/login`'s `password` field accept a key in place of a real password. Same username either way.

```
POST   /auth/api-keys              { label }  -> { key }   (plaintext key, shown once, never retrievable again)
GET    /auth/api-keys              -> { keys: [{ id, label, key_prefix, created_at, last_used_at }] }
DELETE /auth/api-keys/{id}
```

If you're building a client that only supports a single password field anyway (most Subsonic clients), you don't need to do anything special to support this -- it already works today by pasting a generated key into that field.

## Subsonic-compatible API (`/rest/*`)

Base path: `/rest/`. All endpoints accept `f=json` (only JSON is supported, not XML) and both GET and POST. Every response is wrapped:

```json
{ "subsonic-response": { "status": "ok", "version": "1.16.1", "type": "butler", "serverVersion": "1.0.0", ...fields } }
```
or on failure:
```json
{ "subsonic-response": { "status": "failed", "version": "1.16.1", "error": { "code": 40, "message": "Wrong username or password." } } }
```

### Auth
Only the **plaintext password** scheme is supported (`?u=user&p=password`, or `?p=enc:<hex>`), not the salted-token scheme (`?t=&s=`). This is permanent: Butler stores bcrypt password hashes, which are one-way by design, and the token scheme requires the server to compute `md5(password + salt)`, which needs the plaintext password. Most Subsonic clients have a "use plaintext password" fallback option -- enable it.

An [API key](#api-keys) works as the `p=` value too, and is the only option at all for SSO-only accounts, which have no real password to send here.

### Implemented endpoints
Every response includes `"openSubsonic": true` (mandatory per the OpenSubsonic spec -- some clients gate features, including playlists, on this being present). `getOpenSubsonicExtensions.view` advertises what's genuinely implemented: currently just `songLyrics` (structured lyrics via `getLyricsBySongId`, below). Note that Butler's API keys are *not* the spec's `apiKeyAuthentication` extension (that's a separate `apiKey=` query param plus a `tokenInfo.view` endpoint) -- ours work as a plain password substitute instead, so they're deliberately not advertised as that extension.

| Endpoint | Notes |
|---|---|
| `ping.view` | Health check |
| `getLicense.view` | Always reports a valid, unrestricted license |
| `getMusicFolders.view` | Single folder, "Butler" |
| `getUser.view` | Reflects real admin status (`adminRole` = your user id is 1) |
| `getArtists.view` / `getIndexes.view` | ID3-style artist list, alphabetically indexed |
| `getArtist.view` | Artist detail + album list |
| `getAlbumList2.view` | `type=` `random`, `newest`, `frequent`, `recent`, `starred`, `alphabeticalByName`, `alphabeticalByArtist`. `byYear`/`byGenre` aren't supported (Butler doesn't track either) and silently fall back to `alphabeticalByName`. Supports `size`/`offset` paging. |
| `getAlbum.view` | Album detail + song list |
| `getSong.view` | Single song detail |
| `getRandomSongs.view` | `size` param |
| `getGenres.view` | Always empty -- Butler doesn't tag genre |
| `search3.view` | Song title/artist substring search |
| `getPlaylists.view` / `getPlaylist.view` | Your own playlists only |
| `createPlaylist.view` | `name`, optional repeated `songId` |
| `updatePlaylist.view` | `playlistId`, optional `name`, repeated `songIdToAdd` (append) and/or `songIndexToRemove` (remove by position) -- no arbitrary reordering |
| `deletePlaylist.view` | `id` |
| `star.view` / `unstar.view` / `getStarred2.view` | Backed by Butler's real Liked Songs |
| `setRating.view` | Shimmed onto star/unstar: any rating >=1 stars the song, 0 unstars it. There's no real 5-star scale underneath, so a 3-star rating reads back as just "starred," not "3." |
| `getLyricsBySongId.view` | Real, timestamp-synced lyrics where Butler has them (OpenSubsonic structured-lyrics extension). Falls back to plain unsynced lines, or an empty list if Butler has no lyrics cached for that song yet. |
| `getNowPlaying.view` | Always empty -- no cross-user live "now playing" registry |
| `getPodcasts.view` / `getInternetRadioStations.view` / `getBookmarks.view` / `getShares.view` | Always empty (valid response, not an error) -- these exist so clients that probe them on connect don't treat an unimplemented feature as a broken server |
| `getCoverArt.view` | Proxies the cached YouTube thumbnail |
| `stream.view` / `download.view` | Same handler; triggers a download if the file isn't cached locally yet, so first playback of a song can be slow |

### Not implemented
The older folder-browsing scheme (`getMusicDirectory.view` and friends) -- Butler is ID3-tag-browsing only. Also no jukebox control, no video, no multi-server sharing.

## Native REST API

Everything not under `/rest/` is Butler's own API, used by the official web and Android clients. Everything below except `/auth/register`, `/auth/login`, and the OIDC routes needs `Authorization: Bearer <token>`. Full request/response shapes for anything not detailed here are in `/openapi.json` (Swagger UI at `/docs`) on a running instance -- always the authoritative source since it's generated from the live code, not hand-maintained.

### Library & search
```
GET /library?sort=date|title|artist&downloaded_only=false
```
Your whole library. Each song:
```json
{
  "id": 466, "title": "Matador", "artist": "...", "album": null,
  "duration": 248, "youtube_id": "mXO58YF5aRQ", "downloaded": 1,
  "added_at": "2026-08-01 22:11:36", "thumbnail": "https://...", "file_ext": "mp3"
}
```

```
GET /search?q=<query>
```
Local library matches first, then local metadata catalog, then (if the admin hasn't disabled automatic downloads) live YouTube results -- all merged into one `results` array, in that priority order. Results not yet downloaded include `"source": "local"` or omit `source` entirely for fresh YouTube hits; anything with `"downloaded": 0` will trigger a real download the first time you stream it (see below), unless automatic downloads are off, in which case streaming it 503s.

```
GET  /songs/stream/{youtube_id}   -- the actual audio, polls internally up to ~2 min if a download needs to start first
GET  /lyrics/{youtube_id}?force=false   -- {"plain":..., "synced":..., "source":..., "fetched_at":...} or 404 if none cached yet
GET  /artists/{artist_name}       -- bio + related info (MusicBrainz-backed)
```

### Playlists
```
GET    /playlists                          -> {"playlists":[{id,name,owner_name,song_count,shared,created_at,thumbnail}]}
POST   /playlists            {name}        -> the created playlist row
GET    /playlists/{id}                     -> playlist detail + song list
PATCH  /playlists/{id}       {name?, shared?}
DELETE /playlists/{id}
POST   /playlists/{id}/songs/{youtube_id}   -- song must already exist in your library (search/play it first) -- "Play the song first" 404 otherwise
DELETE /playlists/{id}/songs/{youtube_id}
```

### Liked songs, history, discovery
```
GET /liked?sort=date|title|artist   -> {"songs":[...]}
GET /history?limit=50               -- recently played, newest first
GET /discovery                      -- songs outside your library picked for you, {"songs":[{...,"source":"discovery"}]}
GET /daily-mix                      -- {"playlist": {...}|null, "songs":[...]} -- see the local weighted-scoring algorithm in daily_mix.py; empty until you've built up some play history
POST /daily-mix/regenerate          -- force a fresh mix instead of waiting for the daily refresh
GET /recommendations
```

### Cross-device playback sync
This is what lets the web UI show "playing on your phone" and remote-control it. Not required to build a working client -- only relevant if you want that specific feature.
```
POST /now-playing/heartbeat   {youtube_id, position_ms, duration_ms, is_playing, device, device_id}
```
Call every few seconds while actively playing. Send `device_id` (any stable string identifying this install) so other devices can target commands at you specifically. Send with no `youtube_id` to announce "stopped" -- this only clears the shared state if your `device_id` was the one that set it, so a second idle device polling on the same account can't stomp another device's active session.
```
GET  /now-playing                              -- what's playing across any of your devices right now (30s staleness window)
POST /now-playing/command   {device_id, action: play|pause|next|prev|seek, seek_ms?}
GET  /now-playing/commands?device_id=<id>       -- your device polls this every couple seconds; each command is consumed once read
```

### Admin (user id 1 only)
```
GET/POST   /admin/settings          -- {lossless_downloads, ytdlp_downloads_enabled}
GET/POST   /admin/invites           -- list / generate invite codes
DELETE     /admin/invites/{code}
GET        /admin/users
DELETE     /admin/users/{id}
POST       /admin/scan-uploads      -- re-index the manual upload folder
```

### Account & API keys
```
POST /auth/register           {username, password, invite_code}
POST /auth/login              {username, password}   -- password can be a real password OR a generated API key
GET  /auth/me
POST /auth/change-password    {current_password, new_password}
GET    /auth/api-keys
POST   /auth/api-keys         {label}   -> {key}  (plaintext, shown once)
DELETE /auth/api-keys/{id}
```

## Practical notes

- **Cover art**: both APIs proxy Butler's cached YouTube thumbnail for a track. There's no separate album-art endpoint distinct from per-song art.
- **Streaming**: the first play of any song may be slow -- if it isn't downloaded yet, both `stream.view` and the native streaming endpoint trigger a real download before responding. Expect a multi-second delay on cold songs, not a fast redirect.
- **IDs are not stable across a library rebuild.** Artist/album IDs in the Subsonic layer are deterministically derived from the artist/album name (base64 of a lowercased string), not database primary keys -- they'll stay stable as long as the name doesn't change, but don't assume they match anything in Butler's native API, which uses real row IDs.
- **Rate limits**: none currently enforced beyond normal server capacity. Don't be a jerk about it.
